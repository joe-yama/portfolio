# Design

## Context

動機と実測値は `proposal.md` の Why を参照。

現状のサイズ指定は 1 か所に集まっている。`src/components/PhotoPicture.astro` の scoped style が `picture :global(img) { display: block; width: 100%; height: auto; }` を持つだけで、**高さの上限が無い**。この 1 つのルールが `grid` 変種（ギャラリーのサムネイル）と `full` 変種（トップの代表写真・写真の個別ページ）の両方に効いている。

制約:

- 配信 JavaScript ゼロ（spec `quality-gates`）。解決は CSS だけで行う
- ギャラリーは `grid-template-columns: repeat(auto-fill, minmax(280px, 1fr))` の列を `width: 100%` で埋めている。この `width: 100%` を外すとサムネイルが元画像の幅で表示され、グリッドが崩れる
- `main` は `max-width: 80rem`（1248px）・左右 `padding: 1rem`。ヘッダーは高さ可変（狭い画面で折り返す）
- `<img>` は `width` / `height` 属性を持つ（CLS 対策。spec `photo-pipeline`「読み込み前から占有領域が決まる」）。この属性は維持する

## Goals / Non-Goals

**Goals:**

- 高さの上限を持つ場所を 1 つにし、値だけをページ側が決められるようにする
- 上限の値を、ページごとの「写真の下に必ず置くもの」の高さから導く
- 回帰を e2e で検出できるようにする（単体テストでは CSS の寸法を検出できない）

**Non-Goals:**

- 画像の生成幅（`photo-pipeline` の目標幅の表）と `sizes` 属性の変更
- レイアウト構造の変更（要素の並び替え、2 カラム化、ヘッダー・本文の余白の詰め直し）
- ギャラリーのサムネイルの見た目の変更

## Decisions

### D1: 高さの上限は CSS カスタムプロパティでページから渡す

`PhotoPicture` の `full` 変種の画像にだけ上限のルールを置き、上限の値は `--photo-max-height` としてページ側が指定する。

```css
/* PhotoPicture.astro */
picture :global(img) { display: block; width: 100%; height: auto; }   /* 現状のまま。grid 用 */
picture :global(img.full) {
  width: auto;                                 /* 高さに合わせて幅も縮む = 縦横比が保たれる */
  max-width: 100%;
  max-height: var(--photo-max-height, none);   /* 未指定なら従来と同じ見た目 */
  margin-inline: auto;
}
```

- ページは `.hero` / `figure` に `--photo-max-height` を書く。カスタムプロパティは継承するので、コンポーネントに props を増やさずに済む
- 既定値 `none` により、値を渡し忘れたページは従来どおりの表示になる（安全側に倒れる）
- `grid` 変種には一切当てない。D3 のリスクへの対処でもある

**代替案**: `maxHeight` を `PhotoPicture` の props に追加する → CSS の値を TypeScript の文字列で運ぶことになり、スタイルの置き場所が 2 つに割れる。採らない。

**代替案**: 高さを `main` の残り高さから flexbox で自動計算する（マジックナンバー無し）→ `body` の flex 列で `main` の高さが確定しないため、子要素の百分率高さが解決しない環境がある。挙動が微妙で検証コストが高い。1 行の `max-height` と e2e の番人で足りる。採らない。

### D2: 上限の値は「写真の下に置くものの実測高さ + 余白 2rem」

| ページ | 値 | 根拠 |
|---|---|---|
| トップ `.hero` | `max(12rem, 100svh - 27rem)` | ヘッダー 65 + `main` の上下 padding 64 + 写真の下（ドット絵・名前・肩書・連絡先・導線と余白）302 = 約 25rem。折り返しに備えて 2rem 足す |
| 個別ページ `figure` | `max(12rem, 100svh - 18rem)` | ヘッダー 65 + `main` の上下 padding 64 + キャプション（タイトル・撮影地・撮影情報と余白）121 = 約 16rem。同じく 2rem 足す |

- `svh`（small viewport height）を使う。モバイルのアドレスバーが出ている状態の高さなので、収まる保証が最も強い
- `max(12rem, …)` は下限。高さ 688px 未満の画面では 12rem（192px）で打ち止めになり、写真が 0 や負にならない（spec の「表示高さが 0 になってはならない」に対応）
- 狭い画面では `max-width: 100%` の方が先に効くため、上限は発動しない（390×844 の実測で表示は不変）

プロトタイプをブラウザに注入した実測:

| 画面 | ページ | 写真 | 判定 |
|---|---|---|---|
| 1440×900 | `/ja/` | 1248×832 → 750×500 | 導線の下端 898 / 余白 2px |
| 1280×720 | `/ja/` `/en/` | → 432×288 | 導線の下端 686 / 余白 34px |
| 1024×768 | `/ja/` | → 504×336 | 導線の下端 734 / 余白 34px |
| 1440×900 | 個別（縦写真） | 1248×1872 → 408×612 | キャプションの下端 830 / 余白 70px |
| 390×844 | 両方 | 変化なし | 横スクロールなし |

実装後にこの表を e2e で測り直し、値が想定と違えば数値を調整する。値の微調整は spec の要求（「スクロールなしで見える」）を満たす限り自由とする。

### D3: 切り取らない。縦横比は `width: auto` で保つ

`object-fit: cover` は使わない（PO 決定: 写真は一切切らない）。`object-fit: contain` も使わない。`width: auto` + `max-width` + `max-height` でブラウザが縦横比を保ったまま縮める。

**実装時の罠（プロトタイプで実際に踏んだ）**: `width: auto` が既存の `width: 100%` に**詳細度で負ける**と、高さだけが上限で潰れて**写真が横に引き伸ばされる**（1248×500、表示比 2.496 に対し元画像 1.500）。見た目には気づきにくい。`img.full`（詳細度 0,1,1）で `img`（0,0,1）に勝たせること、そして「表示比 == `naturalWidth`/`naturalHeight`」を e2e で必ず検証することの 2 点で防ぐ。

### D4: 番人は e2e に置く

CSS の実寸は単体テスト（Vitest）では原理的に検出できない。`tests/e2e/` に検査を足し、spec `quality-gates` の「ブラウザ検査が必ず含むもの」にも書く。Playwright の既定ビューポート（Desktop Chrome = 1280×720）が最も厳しいケースなので、1280×720 と 1440×900 の 2 つを両ロケールで測る。

## Risks / Trade-offs

- **[写真が小さくなる]** 1280×720 では代表写真が 432×288 まで縮む → PO が「全部を 1 画面に」を選んだ結果として受け入れる。余白の詰め直しで写真を大きくする案は後続の提案に回す
- **[歪みに気づかない]** 詳細度の事故で横に伸びる → D3 の e2e 検査（表示比の一致）で必ず落とす
- **[サムネイルの回帰]** 共有 CSS を触るためギャラリーが崩れうる → `img.full` に限定し、e2e でサムネイル幅 == 列幅を検査する
- **[`sizes` が過大になる]** 表示幅が最大 750px になっても `sizes` は 78rem のまま → 2 倍 DPI ではむしろ適正で、画質は落ちない。取得量がやや多いだけなので今回は許容し、提案に残す
- **[マジックナンバーの陳腐化]** 写真の下の要素（連絡先リンクの数など）が増えると 27rem が足りなくなる → e2e が両ロケール・2 サイズで落ちるので、実データの変更時に気づける

## Migration Plan

CSS のみの変更で、データ・URL・ビルド成果物の構造は変わらない。切り戻しは PR の revert で済む。
