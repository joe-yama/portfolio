# Design

## Context

動機は `proposal.md` の Why、要求は `specs/` の 2 つの delta を正とする。

既存の経歴ページ `src/pages/[lang]/career.astro` は、`getCareer(lang)` が返した 1 ロケール分のデータを 4 区画に並べるだけの薄いテンプレートで、並び替えと日付の整形は `src/lib/career.ts` の純関数、画面の文字列は `src/lib/site.ts` の `ui` に置いてある。日英の整合は `src/lib/validate.ts` の `validateCareerParity` がビルド時に検証し、破れていればビルドを落とす。特許もこの形に合わせる。

掲載するデータは PO 本人の実在の特許である。出所は Google Patents の発明者検索。2026-09-21 時点で日本語表記 `山根丈亮` は 52 件を返し、その内訳は JP 2 件・残りは CN / TW の同族である。**US 文献が 1 件も含まれない**のは、Google Patents が US 公報の発明者をローマ字（`Josuke Yamane`）で持っているためで、日本語表記だけでは US 出願を丸ごと取りこぼす。PO は日本語表記でヒットした 52 件すべてが自身の発明であることを確認済み。

## Goals / Non-Goals

**Goals:**

- 両表記の検索でヒットした公報を発明（同族）単位にまとめ、日英の `patents` として入稿できる形にする
- 経歴ページが特許の一覧で埋まらないようにしつつ、全件に到達できるようにする
- 掲載内容の正誤を PO が 1 か所で確認できるようにする

**Non-Goals:**

- 特許の個別ページや検索・絞り込みの機能
- 特許データの自動更新（新しい出願の取り込みは、次に同じ調査を手で回す）
- 請求項や要約などの本文の掲載（名称・番号・年月・国だけ）
- 既存の資格・実績の表示形式の変更（資格の年月表示は別の change）

## Decisions

### D1: 発明（同族）単位の 1 エントリにまとめる

52 件を公報単位で並べると、同じ発明が JP・CN・TW と 3 回並ぶ。1 発明 = 1 エントリにし、`countries` に出願国・地域を持たせる。

代表の `number` は JP の公報番号を優先する（日本語の名称と対応が取れ、PO が確認しやすい）。JP が取れなかった同族は、取れた国のうち最も早い公開のものを代表にする。

**代案**: 公報単位で 52 行並べる → 同じ発明の重複が読み手に伝わらず、件数を水増ししているように見える。却下。

### D2: 並び順は「出願国の数の降順 → 出願年月の降順」

PO の指示（国際的に出願されているものを優先）。多国出願は社内で価値が高いと判断された発明であることの代理指標になり、`featured` のような手で維持する印を足さずに済む。

`src/lib/career.ts` に純関数 `sortPatents(patents)` を追加する。既存の `sortByDateDesc` と同じく新しい配列を返し、`Array.prototype.sort` の安定性に依存して同値の記述順を保つ。

**代案**: YAML に `featured: true` を付ける → 数十件を PO が手で維持することになる。却下。

### D3: 展開は `<details>` / `<summary>`、JavaScript は使わない

このサイトはビルド時に静的 HTML を出すだけで、クライアント側の JavaScript を 1 行も持っていない。特許の展開のためにそれを崩さない。`<details>` はキーボード操作・スクリーンリーダー・印刷に対応し、折りたたまれた中身も HTML に含まれるので検索エンジンからも見える。

先頭 5 件は `<details>` の外の `<ul>`、6 件目以降は `<details>` の中の `<ul>` に置く。`<summary>` の文言は `site.ts` に置き、件数を埋める（`さらに {n} 件を表示` / `Show {n} more`）。件数が 5 以下のときは `<details>` 自体を出さない。

**代案**: 全件の別ページ `/{lang}/career/patents/` → ページと導線が増え、`sitemap` も無い今は発見されにくい。代表数件だけ載せて Google Patents の検索結果へ外部リンク → 検索結果の URL は安定せず、同姓同名が混ざったときに他人の特許へ誘導する。どちらも却下。

### D4: 年月の整形は `formatMonth` を新設する

既存の `formatDate` は日まで出し、`formatPeriod` は 2 つの年月を `–` でつなぐ。特許は単独の年月なので、`toLocalDate` を使い回す 3 行の `formatMonth(value, lang)` を `career.ts` に足す。`formatPeriod` の内部にある無名の `format` と重複するが、`formatPeriod` の側をこの関数を使う形に書き換えて重複を作らない。

### D5: 日英の整合は件数一致だけを検証する

`validateCareerParity` の既存ループのキー配列に `patents` を足すだけで済む。`number` / `url` / `countries` が日英で同じ値かは検証しない（`certifications` の `url` も検証していない。ずれても表示は壊れず、検証を足すと日英で意図的に違う値を書けなくなる）。

### D6: 発明者名は日本語表記とローマ字表記の両方で検索する

Google Patents の発明者の索引は公報の言語ごとに表記が違う。JP / CN / TW の公報は `山根丈亮`、US / EP / WO の公報は `Josuke Yamane` で入っている。片方だけで検索すると、もう片方の表記しか持たない国の出願が丸ごと落ちる（日本語表記だけの検索結果に US が 1 件も無いのがその証拠）。

そこで両方のクエリを投げ、**公報番号の和集合**を起点にする。同じ発明が両方のクエリに出た場合は、同族としてまとめる段階で 1 件に落ちるので、重複は問題にならない。

ローマ字表記は同姓同名が混ざりやすい（日本語表記より一致がゆるい）。ローマ字表記だけでヒットして日本語表記の同族に繋がらない公報は、**PO の確認が取れるまで載せない**扱いにし、確認用の表に「要確認」として別枠で出す。

**代案**: 日本語表記だけを使う → US 出願を取りこぼす。ローマ字表記だけを使う → JP / CN を取りこぼし、同姓同名も混ざる。どちらも却下。

### D7: 調査は中間 JSON を経由し、YAML は最後に書く

1. Google Patents の検索 API（`https://patents.google.com/xhr/query?url=q%3Din%3A"<名前>"%26num%3D100`）を D6 の 2 つの表記で叩き、公報番号の和集合を得る
2. 各公報のページから同族（Worldwide applications）・優先日・日英の名称を取り、`scratchpad/patents-raw.json` に貯める
3. 同族でまとめ、`countries` と代表 `number` を決めて `scratchpad/patents.json` にする
4. そこから `career/{ja,en}.yaml` の `patents` を生成する

Google は連続したアクセスを自動クエリと判断して `503`（`Sorry...` ページ）を返す。1 件ずつの取得は間隔を空け、`503` は待ち時間を伸ばしながら再試行する。取れなかった公報は JSON に `"resolved": false` として残し、最後に一覧で報告する（黙って落とさない）。

中間 JSON を挟むのは、YAML を作り直すたびに数十回の取得をやり直さないため、そして PO に見せる確認用の一覧をそこから作るため。中間 JSON は scratchpad に置き、リポジトリにはコミットしない。

### D8: 内容の確認は PR を確認ゲートにする

発明の名称・番号・国が正しいかは PO 本人にしか判定できないが、実装の途中で PO を止めない（`CLAUDE.md` の役割分担）。確定した全件の表（名称 / 番号 / 出願年月 / 国）を change の Issue にコメントし、同じ表を PR 本文にも載せる。PO はマージ時にまとめて確認する。

### D9: 既存の実績 1 件を特許へ移す

`achievements` の「特許出願: 話題推定学習装置及び話題推定学習方法（特開2017-151838）」は `patents` に同じ発明が入るので、`achievements` からは削除する。この発明の登録公報は `JP6549500B2`、同族は JP のみ。`achievements` は日英とも 6 件から 5 件になる。

## Risks / Trade-offs

- **同姓同名の別人の特許を載せる** → PO が 52 件すべてを自身のものと確認済み。さらに D8 の表で個別に確認できる。取り違えた場合の代償は、実名の公開サイトに他人の業績を載せること（大きい）なので、不確かな同族は載せずに報告する。
- **Google Patents の 503 で一部の同族が解決できない** → D7 のとおり未解決として残し報告する。未解決の公報は、JP が取れていれば JP を代表に、取れていなければその公報単体を 1 エントリとして載せる（`countries` は 1 件）。結果として並び順で下に来るだけで、誤った情報にはならない。
- **ローマ字表記の検索に同姓同名が混ざる** → D6 のとおり、ローマ字表記だけでヒットして日本語表記の同族に繋がらない公報は載せず、「要確認」として別枠で PO に出す。PO の確認が取れたものだけを後から足す。
- **英語の発明の名称が機械翻訳調になる** → Google Patents が持つ英語の名称をそのまま使う。これは各国の公報に記載された公式の英語名称か、Google の翻訳のどちらか。前者を優先し、CN 公報の英訳しか無い場合は英語名称として妥当か目視で確認する。
- **`patents` が数十件になり YAML が長くなる** → 経歴の YAML が 3 倍近くになるが、入稿形式を変える（別ファイルに分ける）と `getCareer` と parity 検証の形が変わり、change が大きくなる。今回は同じファイルに置く。
- **`<details>` の中は既定で折りたたまれるので、印刷すると 6 件目以降が出ない** → 印刷用の CSS は今のサイトに無く、要求にも無い。後続の提案に回す。

## Migration Plan

データの追加と表示の追加だけで、URL・ビルド・デプロイの仕組みは変わらない。ロールバックは PR の revert で足りる。
