# Design

## Context

動機は `proposal.md` の Why、要求は `specs/` の 2 つの delta を正とする。

既存の経歴ページ `src/pages/[lang]/career.astro` は、`getCareer(lang)` が返した 1 ロケール分のデータを 4 区画に並べるだけの薄いテンプレートで、並び替えと日付の整形は `src/lib/career.ts` の純関数、画面の文字列は `src/lib/site.ts` の `ui` に置いてある。日英の整合は `src/lib/validate.ts` の `validateCareerParity` がビルド時に検証し、破れていればビルドを落とす。特許もこの形に合わせる。

掲載するデータは PO 本人の実在の特許である。出所は Google Patents の発明者検索。2026-09-21 時点で日本語表記 `山根丈亮` は 51 件（API の `total_num_results` は 52 だが `TWI923233B` が 2 回返る）を返し、その内訳は JP 2 件・残りは CN / TW である。**US 文献が 1 件も含まれない**のは、Google Patents が US 公報の発明者をローマ字（`Josuke Yamane`）で持っているためで、日本語表記だけでは US 出願を丸ごと取りこぼす。PO はこの 51 件すべてが自身の発明であることを確認済み。

取得の途中で Google がこの egress を遮断したため、**同族の解決と US の網羅は今回できていない**。取れた範囲と取れなかったものは `research/publications.md` に記録した。今回どこまで載せるかは D7 の PO 決定による。

## Goals / Non-Goals

**Goals:**

- 取得できた公報を日英の `patents` として入稿できる形にする（同族単位へのまとめは D7 のとおり後続へ）
- 経歴ページが特許の一覧で埋まらないようにしつつ、全件に到達できるようにする
- 掲載内容の正誤を PO が 1 か所で確認できるようにする

**Non-Goals:**

- 特許の個別ページや検索・絞り込みの機能
- 特許データの自動更新（新しい出願の取り込みは、次に同じ調査を手で回す）
- 請求項や要約などの本文の掲載（名称・番号・年月・国だけ）
- 既存の資格・実績の表示形式の変更（資格の年月表示は別の change）

## Decisions

### D1: データ構造は発明（同族）単位にする

同じ発明が JP・CN・TW と 3 行に分かれて並ぶのは、重複が読み手に伝わらず件数を水増ししているように見える。そこで **1 発明 = 1 エントリ**をデータ構造にし、`countries` に出願国・地域を持たせる。代表の `number` は JP の公報番号を優先する（日本語の名称と対応が取れ、PO が確認しやすい）。JP が無い同族は、取れた国のうち最も早い公開のものを代表にする。

この構造は今回の取得状況に左右されない。ただし**今回入稿するデータは同族が未解決**なので、実際には 1 公報が 1 エントリになる（D7）。後続で同族を解決したときは、`countries` を埋めて行をまとめるだけで済み、スキーマも表示も変えずに済む。

**代案**: `countries` を持たず公報単位のスキーマにする → 同族を解決した後にスキーマと spec を作り直すことになる。却下。

### D2: 並び順は「出願国の数の降順 → 出願年月の降順」

PO の指示（国際的に出願されているものを優先）。多国出願は社内で価値が高いと判断された発明であることの代理指標になり、`featured` のような手で維持する印を足さずに済む。

`src/lib/career.ts` に純関数 `sortPatents(patents)` を追加する。既存の `sortByDateDesc` と同じく新しい配列を返し、`Array.prototype.sort` の安定性に依存して同値の記述順を保つ。

**代案**: YAML に `featured: true` を付ける → 数十件を PO が手で維持することになる。却下。

### D3: 展開は `<details>` / `<summary>`、JavaScript は使わない

このサイトはビルド時に静的 HTML を出すだけで、クライアント側の JavaScript を 1 行も持っていない。特許の展開のためにそれを崩さない。`<details>` はキーボード操作・スクリーンリーダー・印刷に対応し、折りたたまれた中身も HTML に含まれるので検索エンジンからも見える。

先頭 5 件は `<details>` の外の `<ul>`、6 件目以降は `<details>` の中の `<ul>` に置く。`<summary>` の文言は `site.ts` に置き、件数を埋める（`さらに {n} 件を表示` / `Show {n} more`）。件数が 5 以下のときは `<details>` 自体を出さない。

**代案**: 全件の別ページ `/{lang}/career/patents/` → ページと導線が増え、`sitemap` も無い今は発見されにくい。代表数件だけ載せて Google Patents の検索結果へ外部リンク → 検索結果の URL は安定せず、同姓同名が混ざったときに他人の特許へ誘導する。どちらも却下。

### D4: 年月の整形は `formatMonth` を新設する

既存の `formatDate` は日まで出し、`formatPeriod` は 2 つの年月を `–` でつなぐ。特許は単独の年月なので、`toLocalDate` を使い回す 3 行の `formatMonth(value, lang)` を `career.ts` に足す。`formatPeriod` の内部にある無名の `format` と重複するが、`formatPeriod` の側をこの関数を使う形に書き換えて重複を作らない。

### D5: 日英の整合は件数一致だけを検証する

`validateCareerParity` の既存ループのキー配列に `patents` を足すだけで済む。`number` / `url` / `countries` が日英で同じ値かは検証しない（`certifications` の `url` も検証していない。ずれても表示は壊れず、検証を足すと日英で意図的に違う値を書けなくなる）。

### D6: 発明者名は日本語表記とローマ字表記の両方で検索する

Google Patents の発明者の索引は公報の言語ごとに表記が違う。JP / CN / TW の公報は `山根丈亮`、US / EP / WO の公報は `Josuke Yamane` で入っている。片方だけで検索すると、もう片方の表記しか持たない国の出願が丸ごと落ちる（日本語表記だけの検索結果に US が 1 件も無いのがその証拠）。

そこで両方のクエリを投げ、**公報番号の和集合**を起点にする。同じ発明が両方のクエリに出た場合は、同族としてまとめる段階で 1 件に落ちるので、重複は問題にならない。

ローマ字表記は同姓同名が混ざりやすい（日本語表記より一致がゆるい）。ローマ字表記だけでヒットして日本語表記の同族に繋がらない公報は、**PO の確認が取れるまで載せない**扱いにし、確認用の表に「要確認」として別枠で出す。

**代案**: 日本語表記だけを使う → US 出願を取りこぼす。ローマ字表記だけを使う → JP / CN を取りこぼし、同姓同名も混ざる。どちらも却下。

### D7: 今回は取得できた 51 件で実装し、全件取得は後日に回す（PO 決定 2026-09-21）

D6 の両表記のクエリを投げた直後から、Google がこの egress を自動クエリと判断して `503`（`Sorry...` ページ）で遮断した。curl・WebFetch とも通らず、15 分間隔 × 6 回の再試行でも回復しなかった。公報ページの取得も同じ遮断に当たるため、同族の解決も行えていない。

PO の決定は「完全な全件取得は後日に回し、**現在取得できている全件を入れて実装する**」。したがって:

- 掲載するのは `research/publications.md` の表 A（日本語表記でヒットした 51 件）。公報 1 件 = 1 エントリとして扱う
- 表 B（ローマ字表記の US 文献）は網羅できていないので**今回は載せない**
- `countries` は確認できた出願国だけを持つ（ほぼすべて 1 件）。spec の並び順の要求は変えない。国数がすべて同じなら第 2 基準の `filedAt` の降順に落ちるだけで、要求どおりに動く
- 同族の解決、JP 公報番号への差し替え、US の追加、`TWI923233B` と `TW202539941A` のまとめは**後続の change** で行う

調査結果を `scratchpad` ではなく `openspec/changes/patents-section/research/publications.md` に置くのは、実装を別セッションで始めるため（`CLAUDE.md` の標準ワークフロー 4）。scratchpad はセッションをまたげない。

### D7b: 日本語の発明の名称は暫定とする（裁定）

表 A の 51 件のうち 49 件は CN / TW の公報で、手元にあるのは Google Patents の英語名称だけである。日本語ページには日本語の名称が要るので、英語の定型名称を対応する日本語の定型名称に直したものを入れる（`Information processing device, recording medium, and information processing method` → `情報処理装置、記録媒体および情報処理方法`）。

**間違っていたときの代償**: 公報の正式名称と語順や送り仮名が食い違う。番号は正しいので、読み手がリンクを辿れば正式名称に行き着く。実在しない特許を載せることにはならない。

後続の change で JP 公報を解決したときに正式名称へ置き換える。Issue と PR 本文にこの裁定を明記する。

**代案**: 日本語ページにも英語名称を出す → 日本語ページとして不自然。全件取得まで待つ → PO が「取得できている分で実装する」と決めた。どちらも却下。

### D8: 内容の確認は PR を確認ゲートにする

発明の名称・番号・国が正しいかは PO 本人にしか判定できないが、実装の途中で PO を止めない（`CLAUDE.md` の役割分担）。確定した全件の表（名称 / 番号 / 出願年月 / 国）を change の Issue にコメントし、同じ表を PR 本文にも載せる。PO はマージ時にまとめて確認する。

### D9: 既存の実績 1 件を特許へ移す

`achievements` の「特許出願: 話題推定学習装置及び話題推定学習方法（特開2017-151838）」は `patents` に同じ発明が入るので、`achievements` からは削除する。この発明の登録公報は `JP6549500B2` で、確認できている出願国は JP のみ（同族は未解決）。`achievements` は日英とも 6 件から 5 件になる。

## Risks / Trade-offs

- **同姓同名の別人の特許を載せる** → PO が表 A の 51 件すべてを自身のものと確認済み。ローマ字表記でしか出ない US 文献（表 B）は今回載せない。さらに D8 の表で個別に確認できる。取り違えた場合の代償は、実名の公開サイトに他人の業績を載せること（大きい）なので、確認の取れないものは載せない。
- **同族が未解決なので同じ発明が 2 行に分かれうる** → 現に `TWI923233B` と `TW202539941A` が同じ出願日で並ぶ。件数がわずかに多く見えるが、番号はいずれも実在する公報で、誤った情報にはならない。後続の change でまとめる。
- **`countries` がほぼすべて 1 件になり、並び順の第 1 基準が効かない** → spec の要求は変えず、第 2 基準の `filedAt` の降順に落ちる。全件取得後に `countries` が埋まれば、データを差し替えるだけで意図した並びになる。
- **日本語の発明の名称が公報の正式名称と食い違う** → D7b の裁定のとおり暫定として入れ、Issue と PR に明記する。後続で置き換える。
- **英語の発明の名称が機械翻訳調になる** → Google Patents が持つ英語の名称をそのまま使う。これは各国の公報に記載された公式の英語名称か、Google の翻訳のどちらか。CN 公報の英訳しか無いものが多いため、英語名称として妥当か目視で確認する。
- **`patents` が 51 件になり YAML が長くなる** → 経歴の YAML が 3 倍近くになるが、入稿形式を変える（別ファイルに分ける）と `getCareer` と parity 検証の形が変わり、change が大きくなる。今回は同じファイルに置く。
- **`<details>` の中は既定で折りたたまれるので、印刷すると 6 件目以降が出ない** → 印刷用の CSS は今のサイトに無く、要求にも無い。後続の提案に回す。

## Migration Plan

データの追加と表示の追加だけで、URL・ビルド・デプロイの仕組みは変わらない。ロールバックは PR の revert で足りる。

## Open Questions

なし。全件取得を後日に回すことは PO が決定済み（2026-09-21）。後続の change で行う作業は `tasks.md` 末尾の「提案」に列挙した。
