# Design

## Context

現状は `proposal.md - Why` のとおり。技術的な前提は 2 つある。

1. `validateCareerParity(ja, en)` は `src/lib/validate.ts` にあり、`experience` / `certifications` / `achievements` の `length` を比べるだけである。`skills` は `z.record(nonEmpty, z.array(nonEmpty))` なので配列ではなく、同じ書き方では比べられない。
2. 表示側（`career.astro`）は `Object.entries(career.skills)` でカテゴリを列挙する。日英は別ファイルで、対応づけはこの列挙順にしか依存していない。

## Goals / Non-Goals

**Goals**
- `skills` の日英の食い違いをビルド時に落とす
- プロフィールと経歴を PO の実データにする

**Non-Goals**
- `skills` のスキーマを変えること（`Record<string, string[]>` のまま。キーを共通 ID にして訳語を引く設計は採らない）
- 学歴を載せること（`experience` は職歴の配列で、学歴の置き場が無い。必要なら別 change）
- 資格の日付を年月までの表示にすること（スキーマが `YYYY-MM-DD` 必須。月までしか分からない資格は 01 日に丸める）
- 写真の追加・差し替え

## Decisions

### D1: `skills` の日英の対応づけは「並び順」で行う

カテゴリ名は訳語になる（`言語` / `Languages`）ので、キーの一致は求められない。`Object.entries` の順で i 番目どうしを対応させ、カテゴリ数と各 i の項目数を比べる。

- 代替案 A（キーを共通の ID にし、表示名を別に持つ）: スキーマ変更が要り、YAML が読みにくくなる。カテゴリは数個で、日英を同時に手で書くので不一致は並び順で十分捕まる
- 代替案 B（カテゴリ数だけ比べる）: 項目数のずれ（日 3 件・英 2 件）が素通りする。実データで最も起きやすいのがこれなので採らない

**間違っていたときの代償**: カテゴリの並びを片方だけ入れ替えると、件数が同じでも誤った対応で検証が通る。ただし表示側も同じ並び順で対応づけているので、検証が通る状態＝表示が意図どおりの状態であり、実害は無い。

**既知の穴**: カテゴリ名が数字だけの場合、JS のオブジェクトは整数キーを先頭に並べ替える。日英とも同じ並べ替えを受けるので対応づけは一致するが、著者の意図した順とは変わる。実データに数字のカテゴリは無い。

### D2: 検証の置き場は `validateCareerParity` を拡張する

新しい関数を足さず既存の関数に足す。呼び出し側（`content.ts`）とテストの構造を変えずに済み、「経歴の日英の一致」という 1 つの要求に対応する実装が 1 か所に集まる。

### D3: TOEIC は `certifications` に入れる

`achievements` の `kind` は `talk` / `article` / `award` / `other` で、スコアはどれにも収まりが悪い。取得の証明という性質は資格と同じ。

### D4: 連絡先は GitHub と LinkedIn のみ

PO 決定。メールアドレスは載せない。勤務先アドレスは公開用に使わない。

## Risks / Trade-offs

- **実名・勤務先・資格・論文が公開リポジトリと GitHub Pages に載る** → 出典は PO 本人の公開 LinkedIn プロフィールで、掲載内容は PO が項目ごとに決定済み。取り消す場合は YAML の差し替えで元に戻せる
- **日付の一部が推定** → 資格は月までしか分からないので 01 日に丸める。特許の日付（2017-08-31）と NLP2016 の日付（2016-03-01）は PO が確認済み
- **既存の単体テストがサンプルデータの値に依存している** → 差し替えで落ちる。落ちたテストは実データに合わせて期待値を直すのではなく、まず「何を守っていたテストか」を見て、データに依存しない形に直せるなら直す

## Migration Plan

`main` への PR 1 本。デプロイは `main` への push で自動。ロールバックは PR の revert（データファイルの差し替えだけなので副作用が無い）。
