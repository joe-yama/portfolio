# Design

## Context

Change 8 でスキーマ（`patentSchema`）・純関数（`sortPatents` / `splitPatents` / `formatMonth`）・表示（`<details>` による折りたたみ）・日英の件数一致の検証はすべて入っている。**この change で変えるのはデータと、その周辺の番人だけ**で、構造は変えない。

2026-09-22 時点で確認できた取得の条件:

- 発明者クエリ `https://patents.google.com/xhr/query?url=q%3Din%3A"<名前>"%26num%3D100` は 200 を返す。`山根丈亮` で 51 公報、`Josuke Yamane` で 66 公報、**両者の重複はゼロ**（和集合 117）
- 公報ページ `https://patents.google.com/patent/<番号>/en` も 200 を返し、次の構造化データを含む
  - `itemprop="inventor"` — 発明者一覧
  - `itemprop="applications"` の行 — 同族の各国出願。`applicationNumber` / `representativePublication` / `primaryLanguage` / `priorityDate` / `filingDate` / `title`（**その国の言語の正式名称**）
  - `itemprop="countryStatus"` の行 — `countryCode` と各国の代表公報
- 前回の遮断は自動クエリと判断されたことによる。同じ遮断を避けるため、取得は 1 件ずつ 5〜9 秒の間隔を空け、403 / 429 / 503 は指数バックオフで待つ

Change 8 のデータは「1 公報 = 1 エントリ」なので、spec の「1 つの発明につき 1 件」「`filedAt` は同族のうち最も早い出願の年月」に違反している。**この change はデータを spec に合わせる作業**であり、spec の要求を緩めない。

## Goals / Non-Goals

**Goals:**

- 発明者索引に載る公報を漏れなく起点にし、同族単位の 1 件にまとめる
- 日本語の発明の名称を公報の正式名称にする（裁定 D7b の解消）
- `countries` の先頭が代表公報の国と一致することをビルドの番人にする（裁定 R5 の解消）
- データ差し替えで壊れる番人と、片方だけ直す事故を招く重複を同じ change で片付ける
- 掲載する全件を PO が 1 か所で確認できるようにし、落とした公報は理由とともに残す

**Non-Goals:**

- 特許の個別ページ、検索・絞り込み、請求項や要約の掲載
- 特許データの自動更新（新しい出願の取り込みは次に同じ調査を手で回す）
- 取得スクリプトのリポジトリへの取り込み（D10）
- スキーマ・並び順・折りたたみの仕様の変更
- 印刷用 CSS（Change 8 が後続に回した分。この change には含めない）

## Decisions

### D1: 同族の単位は Google Patents の `Country Status` をそのまま使う（2026-09-22 修正）

同じ発明の各国出願をまとめる基準は、自分で作らずに Google が解決した同族をそのまま使う。

**当初この design は `Worldwide applications`（`itemprop="applications"`）の行を同族と読んでいたが、それは誤りだった。** 実データで確かめたところ、この表はその公報**自身の出願 1 件**しか持たない（例: `CN111238513B` の `applications` は CN 出願の 1 行だけ）。同族は `Country Status`（`itemprop="countryStatus"`）の表で、各国の `countryCode` とその国の代表公報 `representativePublication` が並ぶ（同じ例で US / JP / CN の 3 行）。

したがって**同族の識別子は `countryStatus` の `representativePublication` の集合**とし、集合が交わる公報を推移的に 1 つにまとめる。`docdbFamily`（Also Published As）と Publications の表も同じ同族の別公報を指すので、識別の補強に使う。

`Country Status` が無い公報（TW の 2 件）は、同族を解決できないものとして扱い、`docdbFamily` と出願番号で突き合わせる。

**代案**: 優先日と出願人と名称の一致で自前に束ねる → 名称は国ごとに訳が違い、優先日は分割出願で揃わない。誤結合と取りこぼしをこちらで背負う。却下。

**間違っていたときの代償**: Google が同族を取り違えていれば、別の発明が 1 行にまとまる。公報番号は残るので読み手が辿れば気づける。

### D2: 発明者の照合は機械で行い、落とした公報を表に残す

発明者クエリは筆頭発明者しか結果に出さないので、117 公報に PO 以外の発明が混ざっていないことを公報ページ側で確かめる。`itemprop="inventor"` の値から空白と中黒を除き、小文字化したうえで、`山根丈亮` / `丈亮山根` / `josukeyamane` / `yamanejosuke` のいずれかに一致する発明者が 1 人以上いる公報だけを採用する。

落とした公報は `research/publications.md` に公報番号・名称・発明者一覧・落とした理由を残す。**同族の中に 1 つでも一致する公報があれば、その同族は採用する**（各国の公報で発明者の表記や順序が違うため）。

**代案**: PO が 117 件を目視で判断する → 作業量が大きく、根拠が残らない。却下（PO 決定 2026-09-22 で機械検証を選択）。

**実データで分かったこと（2026-09-22）**: この照合が、**Change 8 が載せていた `JP7151181B2`「音声対話システム、その処理方法及びプログラム」を落とした**。この公報の発明者は渡部生聖・樋口佐和・堀達朗の 3 名で、PO は含まれない。`山根丈亮` はこの公報の**説明文中の引用文献**（「上位語・下位語の射影関係とそのクラスタの同時学習、山根丈亮、高谷智哉、…、第 22 回言語処理学会年次大会、2016」）の著者として 1 か所だけ現れる。Google の発明者検索が全文の一致で拾ったものが、Change 8 の PO 一括確認をすり抜けていた。**除外が正しい**（裁定 R11）。

### D3: 代表公報は JP を優先し、Google が国ごとに選んだ代表をそのまま使う

`number` には、`countryStatus` の行のうち `countryCode` が `JP` のものの `representativePublication` を入れる。JP が無い同族は、`applications` の行のうち `filingDate` が最も早い国の代表公報を使う。

JP の公開公報（`JP2017151838A`）と登録公報（`JP6549500B2`）のように同じ国に複数の公報がある場合、どちらを代表にするかは Google が `countryStatus` で 1 つに決めている。自分で優劣を決めずにそれに従う。

### D4: `countries` は代表公報の国を先頭にし、残りは出願の早い順に並べる

spec は先頭だけを縛っている。残りの順序を決めないと、取得のたびに並びが変わって差分が読めなくなる。`applications` の `filingDate` の昇順（同じ日はコードの辞書順）で安定させる。

### D5: `filedAt` は同族の `priorityDate` の最小値の年月（2026-09-22 修正）

spec は「同族のうち最も早い出願の年月」と定める。D1 の修正で分かったとおり、1 つの公報ページから読める `filingDate` は**その公報自身の出願日**でしかない（`CN111238513B` なら CN 出願の 2019-10-18）。同族の最も早い出願日は、同じページの `priorityDate`（2018-11-29 = JP 出願の出願日）に現れる。優先日は同族のどのメンバーのページでも同じ値になるので、これを使うと 1 ページから同族全体の最早出願年月が決まる。

したがって `filedAt` = 同族のメンバーから読めた `priorityDate` の**最小値**の `YYYY-MM`。

**間違っていたときの代償**: 優先権の基礎出願が同族に含まれない（別の発明の出願を優先権主張の基礎にしている）場合、表示される年月が実際の出願より早くなる。番号は正しいので読み手はリンク先で確かめられる。当初の `filingDate` 案のままだと、CN 公報だけの同族で年月が 1 年ほど新しくなり、**同じ発明が日英・国ごとに違う年月で並ぶ**という spec 違反に近い状態になっていた。

### D6: 名称は同族の代表公報のページから言語ごとに取る（2026-09-22 修正）

Google Patents は発明の名称を**ページの表示言語に合わせて**出す。`/en` で取ったページには日本語の名称が 1 行も入らない（実装者が 117 ページで確認: 日本語の行 0 件）。また `Country Status` の各国の代表公報は、起点の 117 公報に含まれていないことがある（JP 代表 64 件のうち 43 件が corpus 外だった）。

したがって:

- `title.ja`: 同族の **JP の代表公報のページを `/ja` で取得**し、その名称を使う
- `title.en`: 同族の **US → EP → WO の代表公報のページを `/en` で取得**し、その名称を使う。どれも無ければ、起点公報の `/en` ページに Google が出している英訳を使う

JP の代表が無い同族の日本語の名称は、Change 8 と同じく英語の定型名称から起こしたものを入れる（**D7b は完全には解消しない**）。何件残るかは実装時に数え、`tasks.md` と PR に書く。

### D7: 英語ページのリンクは `en.yaml` の `url` を `/en` にして実現する

表示側で `url` の末尾を言語に応じて差し替えるより、データを言語ごとに持つほうが素直で、Google Patents 以外の URL が混ざったときも壊れない。`validateCareerParity` は `url` を検証しないので、日英で値が違っても通る。

**代案**: `PatentItem.astro` で `url.replace(/\/ja$/, '/en')` する → Google Patents の URL 形式に表示コードが依存する。却下。

**間違っていたときの代償**: 日英の `url` が同じ特許を指していないことに気づけない。spec の Scenario（日英のリンク先が異なる）を e2e で見張る。

### D8: `countries[0]` の検証は `validate.ts` の純関数にする

`validateCareerParity` は日英 2 つの経歴を比べる関数で、これは 1 つの経歴の中で閉じる検証なので別の関数にする。`validateCareerPatents(career, lang)` を足し、`number.slice(0, 2)` と `countries[0]` を比べ、違えば `number` と `countries[0]` を含むメッセージを返す。日英の両方に対して呼ぶ。

### D9: 特許の `<li>` を `src/components/PatentItem.astro` に切り出す

いま `career.astro` に同じマークアップが 2 か所ある（先頭 5 件用と `<details>` の中用）。この change で `url` の扱いが言語ごとに変わるので、2 か所を別々に直す事故が現実に起きうる。切り出して両方から呼ぶ。

### D10: 取得スクリプトはリポジトリに入れず、手順を `research/method.md` に残す

次に同じ調査を回すのは新しい出願が増えたときで、そのときは Google のページ構造も変わっている可能性が高い。動かないスクリプトを抱えるより、**どのエンドポイントから何を取り、どう束ねたか**を文章で残すほうが役に立つ。スクリプトは scratchpad の使い捨てとする（Change 8 の `verify-data.mjs` と同じ扱い）。

### D11: 掲載する全件は PR の本文で PO が確認する

Change 8 と同じ形式の表（公報番号・名称・年月・国）を `research/` に置き、PR の本文から参照する。落とした公報の表も並べる。

## Risks / Trade-offs

- **取得中に再び遮断される**: 117 公報を 1 件ずつ取るので 15〜25 分かかる。途中で遮断されたら、取得済みのページはそのまま使い、残りを時間を空けて再開する（スクリプトは取得済みを飛ばす）。**部分的なデータで入稿してはならない** — 同族が欠けると `countries` が不完全になり、並び順が狂う
- **件数が大きく減る**: 51 件が同族単位でおそらく 60〜70 件（US / EP が加わるため増える可能性もある）。先頭 5 件の顔ぶれが変わり、多国出願の発明が上に来る。これは D2（Change 8）の意図どおり
- **日本語の名称が変わる**: 暫定の名称が正式名称に置き換わるので、既存の行の文言がほぼ全部変わる。差分は大きいが、番号が正しいので検証はリンク先で行える
- **`countries[0]` の検証を足すと既存データが落ちる可能性**: いまのデータは 1 公報 1 エントリで `countries` が 1 件なので必ず一致する。検証の追加自体は既存データを壊さない
- **番人が本当に番人か**: Change 9 の教訓に従い、追加した検査に変異を当てて落ちることを確かめるタスクを置く（`tasks.md` の 5.x）
